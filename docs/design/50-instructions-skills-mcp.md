# Instructions, skills and external tool servers

The three ways a user extends the agent: the project file, skills, and servers that speak the tool protocol (MCP).

## Where katana is today

- **Project file**: `KATANA.md` or `AGENTS.md` up to the repository root goes into the system prompt after the
  environment block, 5,000 bytes at most (`src/agent/project.c`).
- **In progress, not merged, not tried with a model** (the "extending" work of 2026-11-21): the *brief* format
  (`build:`, `test:`, `rules:`, `never:` and `ask:` with patterns the engine enforces in the dispatcher, `done:`,
  `docs:`; three layers; `katana init`, `katana brief check`); the *ability* format for skills (`when`, `needs`
  checked by the engine, numbered `steps` with `=> check` that become the task list, `done`, `report`, `fail`);
  the *card* for a server (one signature line per tool, 473 characters for a 7-tool server against about 1,560 as
  JSON schemas, estimated there). The end-of-request check of `done:` is written and not wired.
- **MCP client** (`src/agent/mcp.c`): stdio and HTTP, lists, resources, prompts; servers connect on demand.
- **Skills**: `Skill` loads `SKILL.md`; one line in the environment block lists up to 10 skills.

## What the frontier does

- **Deployed.** Instruction files are a de facto standard across agents. Skills with progressive disclosure (only a
  name and a one-line description in context until used) were donated to a foundation and adopted widely [18].
  Declarations of external tools are the largest fixed cost of hosted agents: one common server costs 19,000 to
  26,000 tokens; deferring declarations until searched cut 77,000 tokens to 8,700 in a vendor measurement, and
  exposing a whole interface as two tools (search, execute code) cut over a million tokens of schemas to about a
  thousand [2][4]. The 2026 revision of the tool protocol removes sessions and the handshake (stateless servers)
  and moves long-running tasks and embedded interfaces into extensions [19].
- **Published.** A controlled study of instruction files on four agents, one of them an open model run locally:
  files generated by a model changed success by -0.5 to -2 points (not significant) and raised cost by 20 to 23%;
  files written by developers gave +2.4 points (not significant) at up to 19% more cost; repository overviews did
  not reduce the steps needed to find files. Its conclusion: keep such files minimal and operational [17].
- **Unsolved.** Whether small models trigger skills from a one-line list. How to know which lines of an
  instruction file do anything.

**For a slow engine:** an instruction the engine can execute costs no tokens and is always obeyed; an instruction
the model must read costs tokens in every session and is obeyed sometimes. The formats in progress go in the right
direction. The changes below push them further the same way.

## Design

### Now

**X1. The brief sends only what the engine cannot do itself.**
- What: of the brief's keys, `never:` and `ask:` items that carry a pattern, `build:`, `test:`, `lint:` and
  `done:` are consumed by the engine (rules in the dispatcher and, with F7 of `30-call-formats.md`, in the sampler;
  commands in V1 and L8). They are shown to the model as **one line each**, because it must know they exist, not
  re-derive them. `layout:` is dropped from the format: the environment block already carries a folder map, and
  the evidence says overviews do not reduce search steps [17]. Budget of the rendered brief: 600 characters, not
  1,500.
- Mechanism: P1, P4. Cost: `brief.c` renders a model view distinct from the file. Measure: with experiment 1's
  micro-set, a brief on and off for the `extend-*` projects: solved, rounds, tokens. Drop the model view entirely
  (enforce silently) if it makes no difference.

**X2. `katana init` detects; it does not ask the model to write.** The model-improvement step of `/init` produces
exactly the generated file the evidence found useless and costly [17], at 40 ms a token. `init` writes the detected
commands and stops; the owner adds rules. Cost: remove the second step. Drop: n/a.

**X3. Wire the end check as a verdict.** `brief_end_note` becomes L8 of `10-agent-loop.md`: the engine runs the
`done:` command and feeds the verdict; it does not remind the model to run it.

**X4. Steps the engine can run, it runs.**
- What: in an ability, a step written `run: <command> => <check>` is executed by the engine when the skill
  reaches it; a step written `do: <instruction> => <check>` goes to the model. A skill made only of `run:` steps
  completes in one round: the model reads one verdict per step (`1 ok, 2 ok, 3 fail: <first line>`). Checks that
  are commands are run by the engine for both kinds and mark the step done (L6).
- Mechanism: P1. A release checklist does not need 25 tokens a second to type `git status`.
- Cost: a step kind in the ability parser and a runner (the `Do` runner of `20-tools.md`, B1, or `bash.c`
  directly). Three days. Measure: rounds per skill run on three written skills. Drop: if owners do not write `run:`
  steps, the kind stays and costs nothing.

**X5. Skills that load themselves.** An optional `on: <glob over the user's message>` key; when it matches, the
engine loads the skill before the first turn and says so in the user's message. Saves the round of calling `Skill`
and does not depend on the model noticing the one-line list. Measure: on scripted requests, share that used the
right skill with `on:` and with the list only. Drop if false matches annoy the owner (count from sessions).

**X6. One declaration format for all tools: the card.**
- What: katana's own tools are declared to the model in the card form
  (`Read(file_path, offset?:integer, limit?:integer) - read a file by lines`) instead of JSON schemas, inside the
  block the model's template expects. The call grammar holds the full schema, so validity does not depend on the
  model reading it.
- Mechanism: the declarations are about half of the 2,500-token prompt. Cards are about a quarter of the size of
  schemas (measured on the 7-tool test server: 473 against about 1,560 characters). This is the middle path between
  full declarations and none: it needs no training night and keeps the meaning of each parameter in view. It
  buys context room, not time (the prefix is cached).
- Evidence: signature-style declarations are what the code-interface designs feed their models [4]; no measurement
  for these two models. Cost: `ct_decl` in `src/tools/table.c` gets a card renderer (shared with the MCP card
  code). Two days.
- Measure: experiment 1's micro-set, three arms on the chosen base model: JSON declarations, cards, none (with the
  grammar on in all three): solved tasks, `error[args]` rate. Drop cards if they lose tasks against JSON.

**X7. Server results go through shaping and handles.** `structuredContent` and long text results of external tools
are stored behind a handle and shaped as "unknown" or as a table (T2, T3 of `20-tools.md`). External tools can be
steps of a batch (B1), which gives the round savings of code-driven tool use without a sandbox.

**X8. Follow the stateless protocol revision; build nothing on sessions.** The client keeps working with both;
no work on server-initiated sampling, tasks or embedded interfaces until a server the owner uses needs one.

### Next

**X9. Rule accounting.**
- What: `katana brief report` reads the session files and prints, per line of the brief: how many times the
  engine enforced it (`never`, `ask`), how many times a checkable rule was violated in sessions where it was in
  the prompt, and (from scheduled ablation sessions, where the line is withheld) how often it is violated without
  it. A line that is never violated either way is flagged for removal from the model view.
- Mechanism: P2 and P5 applied to instructions. The published study could only measure whole files [17]; the
  engine sees every call and can measure single lines.
- Cost: a checker per rule type (a pattern over calls; rules without a pattern cannot be counted and are reported
  as such). One week. Measure: prompt bytes removed with no change in violation counts.
- Confidence: medium. Original as far as the landscape report shows.

**X10. Skills mined from sessions, reviewed by the owner.** `katana skill mine`: the same successful command
sequence (normalised: paths and versions as arguments) seen in three or more sessions of the knowledge notes
becomes a proposed ability file with `run:` steps, for the owner to accept or delete. No model involved. Measure:
proposals accepted. Drop if acceptance is under one in five.

### Beyond

**X11. Skills and rules that graduate into the weights.** When a `do:` skill has been run successfully N times, its
recorded runs become a curriculum family (`60-training.md`); after a night in which the held-out probe shows the
model performs the steps without the skill text, the skill is marked `learned:` and stops being loaded. The same
for `rules:` lines whose violation rate without the line (X9) reaches the rate with it. The prompt shrinks as the
model learns, and the accounting says when. Confidence: low to medium; it depends on training moving behaviour at
this budget, which is experiment 2.

**Rejected:** an include syntax for instruction files (the `docs:` pointers are the lazy form); long generated
project overviews [17]; loading server declarations eagerly; a marketplace or plugin bundle format before a second
user exists.
