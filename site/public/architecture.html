katana architecture

How everything connects, and what exists in each layer. Every component carries the status the repository supports: working, partial, planned or disabled. Planned and disabled parts are shown as such.

The diagram

Solid arrows are data flows that exist today, dashed arrows are planned. Status is read from the code, the tests and the measurements recorded in the repository; where a part was built but never measured or never run with the real model, it is marked partial. The same diagram as a file is in the repository: docs/img/architecture.svg.

What the status means

Status is read from the repository (code present, tests, measurements recorded in the docs). Two project rules apply: no tests or measurements were required in the latest phase, and only Qwen3.6-35B-A3B counts as the working model (CLAUDE.md). So "working" has a narrow meaning here.

StatusMeaning
workingBuilt, and a test, selftest or measurement recorded in the repository shows it doing its job. It may still never have been run with the real model; the notes say so.
partialBuilt, but not measured, not run with the real model, or limited to part of the design.
plannedDesigned in a document, not built.
disabledBuilt and measured, and turned off because the measurement did not justify it.

Layers are listed from the bottom up: each one uses the ones below it. A request enters at the top and goes down through the UIOE, the model and the tools. The image engine and UCGE are side subsystems: the image engine is reached through the Render tool and the desktop, UCGE is not connected to the agent yet.

L3. UIOE

Design in docs/uioe.md. Request flow: user input, Interpret, Classify, Route, Retrieve, Orchestrate, sources, Context Builder, model. In C, in milliseconds, with no model call. How a request moves

Text request. User input (console, desktop, -p, server) -> UIOE interprets, classifies, routes and retrieves (L3, over the code index of L4) -> Context Builder appends the block or nothing -> the model (L1, on Vulkan or the CPU) answers or calls a tool (L2) -> the result returns as data -> repeat until a text answer.

Image request. The user attaches a view -> the agent (or the desktop directly) writes a brief -> Render with stable produces a preview -> the user approves -> Render with flux produces the final image.

Code request, today. The model reads with Find/Symbols, changes code with Edit (by symbol, validated before writing). Code request, planned. The model writes a spec -> UCGE parses it, builds the typed UIR and the AST, generates the language, validates it -> the result goes in through Edit by symbol. The UCGE half of this flow does not exist in the agent yet.

What this audit could not verify

  • Nothing here was measured again. Numbers are quoted from the documents named next to them, taken on one machine (RTX 3050 Laptop 4 GB, i7-11800H, 64 GB RAM, Linux).
  • The engine was not rebuilt and the tool tests were not run for this page; only sh tools/ucge/test.sh was run (60 checks, all passed). Every other "working" rests on the tests and measurements the documents record.
  • Whether any of the UIOE, the tool set or the index improves the real model's answers is unknown: no measurement with Qwen3.6 is recorded.
  • The state of the older 3-token repetition draft of the dense Vulkan graph (KATANA_SPEC, mentioned in README.md under "Speculation") was not checked.
  • Branches feat-ucge-* and other worktrees were not inspected; the UCGE rows mean this tree only.
  • Documents with older status lines: docs/code-intelligence-architecture.md (says "design only"), docs/embedding-usage.md and README.md (say embeddings are not connected), src/katana.c (STUB comments).
